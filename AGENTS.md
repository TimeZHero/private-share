# Private Share — Project Decisions

## Security Model

- **End-to-end encryption**: All secret content and files are encrypted client-side (AES-256-GCM, PBKDF2 key derivation) before reaching the server. The server stores only ciphertext.
- **Zero-knowledge**: The server must never be able to recover or read secrets, text or files. Encryption keys exist only in the URL fragment (`#key`) which is never sent to the server.
- **Burn after reading**: Secrets are permanently deleted after a single retrieval. Files are deleted after a single download.
- **Password protection**: When enabled, passwords are bcrypt-hashed server-side. Wrong password attempts must not delete or reveal the secret.
- **No sensitive data in logs**: Logs must never contain secret content, encryption keys, plaintext passwords, or file contents. Audit only IDs, timestamps, and IP addresses.
- **Share key**: `generateKey()` returns 16 bytes from `crypto.getRandomValues` as base64url (22 chars), fed to the same PBKDF2 derivation as before. Links created before this change carry an 8-char alphanumeric key; `isValidKey()` accepts both so they keep decrypting. The legacy pattern can be dropped once no secret predates the change by more than the 30-day expiry.
- **Accepted risks**: File name, mime type and size are stored in plaintext and returned by `/check` before the password. The secret password is a server-side second layer, not part of the key derivation. Operator or host compromise cannot be defended against in browser-delivered E2E (hence "self-host"). Deployment concerns are documented in README "Going Live" instead of enforced in code: storage privacy for any `FILE_DISK` driver and TLS/HSTS at the edge. Log retention and log integrity are left to whoever runs the instance. Inherent to the design: an intercepted share link exposes the secret (the password is the defence) and encrypted files cannot be scanned for malware. The threat model records these as NotApplicable with the reasoning.
- **Trusted proxies**: Local trusts every proxy (`TrustProxies::at('*')` in `bootstrap/app.php`). Elsewhere `config/trustedproxy.php` reads `TRUSTED_PROXIES` and defaults to trusting none (forwarded headers ignored) — a deliberate choice over `*`, because in this Laravel version `*` trusts `0.0.0.0/0` and the client IP becomes the leftmost, client-controlled `X-Forwarded-For` entry, which defeats per-IP rate limiting. Symfony's `PRIVATE_SUBNETS` includes the RFC 5737 documentation ranges, so tests use real public IPs.
- **Upstream baseline**: setup best practices come from [TimeZHero/laravel-production-ready](https://github.com/TimeZHero/laravel-production-ready). `main` takes the app-level ones: `"composer": ">=2.11"` in `require` (older Composer silently ignores the cooldown policy), `Schedule::alwaysOnOneServer()` (lock in the shared `CACHE_STORE`; name any closure task or it runs everywhere), and upstream's `.gitignore`/`.gitattributes` conventions. `main` deliberately keeps Sail's Ubuntu dev image instead of upstream's Alpine `development` target, because Playwright's Chromium cannot run on Alpine (musl) and the browser suite runs inside the dev container. Production images, supervisord and container startup belong to the deployment branch, not to `main`. Deliberate divergence: upstream suggests `trustProxies(at: '*')`, which in this Laravel version lets clients choose their IP via `X-Forwarded-For`; keep `TRUSTED_PROXIES`.
- **Local dev environment**: Sail's Ubuntu image, served at `https://<folder>.localhost` by a shared caddy-docker-proxy (external `caddy` network, labels in `compose.yaml`, no published ports). `compose.yaml` injects `APP_URL`, `SESSION_DOMAIN`, `VITE_DEV_SERVER_URL` and `MAIL_HOST` (container env wins over `.env`). Mailpit is reached through the project-only alias `mailpit.internal`: the bare service name also registers on the shared `caddy` network and would resolve to other projects' Mailpit. The container command is `php artisan dev` via Sail's `SUPERVISOR_PHP_COMMAND`; `DevServiceProvider` rebinds the server to `0.0.0.0:80` (where Caddy connects) and adds `schedule:work`. `@laravel/multiplex` is a pinned devDependency because `artisan dev` runs it through `npx`, which would otherwise download the latest version on every start, outside the lockfile and the cooldown. `vite.config.ts` sets `server.origin`, HMR on port 443 and CORS for `APP_URL` only when `VITE_DEV_SERVER_URL` is set; `app.blade.php` needs `@viteReactRefresh` (its inline preamble carries the CSP nonce). `tests/TestCase.php` points Vite at a missing hot file so tests render built assets even while the dev server runs. The repo ships the `sail` script (refreshed by a `post-update-cmd` hook).
- **Dependency cooldown**: Composer (`config.policy.cooldown.period`, needs Composer ≥ 2.11) and npm (`min-release-age` in `.npmrc`, days) refuse releases younger than 1 day. One day (lowered from 3 on purpose) lets security releases, such as Symfony's batched advisories, land quickly while still skipping releases that get pulled within hours of publishing. The Sail image installs whatever Composer is current when it is built, so an image built before Composer 2.11 rejects `composer.json` (`composer >=2.11`): rebuild it (`sail build --no-cache`), or for the running container `docker exec -u root <app container> composer self-update`. When a security fix is still inside the window, either wait or bypass once (`composer update <pkg> --no-cooldown`); do not add packages to `policy.cooldown.ignore` without asking. `composer update --no-blocking` also drops the cooldown, so to bypass only advisory blocking set `policy.advisories.block` to false temporarily and unset it afterwards.
- **Burn after reading is atomic**: `Secret` and `SharedFile` use the `BurnsAfterReading` trait. `claim()` runs one `DELETE ... WHERE id = ?` and only the caller that removed the row may serve the content; `burn()` additionally fires the `deleted` model event (observer logging, storage cleanup). Never read-then-delete. The S3 download path uses `claim()` because the object must survive until the signed URL expires (a delayed `DeleteStorageObject` job removes it). `SecretRetrieved` only logs; there is no burn listener.
- **Password guessing**: `SecretPasswordAttempts` (called from `SecretController::retrieve`) gives each client 5 free failures, then lockouts of 60 s doubling per failure up to 24 h; the failure counter slides (Cache increment + touch, 24 h) and is never reset by a successful retrieval, otherwise an attacker could reset it with a secret of their own. The 10th failure on one secret from any clients locks that secret for the rest of the hour (accepted trade-off: the real recipient can be locked out). Lockouts are checked before the password and answer 429 via `PasswordAttemptsExceeded` (`too_many_wrong_passwords` / `secret_locked`).
- **Rate limiting**: every route uses a `RateLimit` enum case (`->middleware(RateLimit::X->middleware())`); limits live in the enum's `match`, registered in `AppServiceProvider`. Clients are identified by `ClientIdentity` (account when signed in, else IP with IPv6 collapsed to /64). `RateLimitCoverageTest` fails on any unthrottled route; extend its exemption list only for framework/local-only routes. All JSON 429s share `TooManyAttemptsResponse` (`error`, `message` with a human wait, `retry_after`, `Retry-After` header); the viewer shows them as `retrieveError` above the reveal button. Upload chunks allow 1000/min because 8 MB chunks at that rate already exceed 1 Gbit/s.
- **Secret content column**: `secrets.content` is MEDIUMTEXT because content is validated up to 1 MB of ciphertext and MySQL TEXT stops at 64 KB. SQLite (local dev, tests) has no such limit, so size bugs only show on MySQL.
- **Security headers and CSP**: `AddSecurityHeaders` (global middleware) sends `X-Frame-Options: SAMEORIGIN`, `nosniff`, `Referrer-Policy: no-referrer` (secret URLs carry the id), a restrictive `Permissions-Policy`, and a full CSP whose goal is that injected code can neither run nor send the key anywhere:
    - `script-src 'self' 'nonce-…'`: `Vite::useCspNonce()` is called before the request is handled so `@vite` tags carry the per-request nonce. Never add inline `<script>` without `nonce="{{ Vite::cspNonce() }}"`, and never add `'unsafe-inline'`/`'unsafe-eval'` to scripts.
    - `style-src` keeps `'unsafe-inline'` because sonner injects its CSS at runtime without nonce support (and the branding `<style>` is inline); CSS can only leak via `url()` loads, which `img-src`/`font-src` restrict.
    - `img-src 'self' data: blob:` plus `https://*.googleusercontent.com` (Google avatars) only when Authentication is on, so remote images in markdown secrets do not load (by design: it closes the image exfiltration and tracking-pixel channels). For the same reason the markdown toolbar has no image action; do not add one back. `font-src`/`style-src` allow `https://fonts.bunny.net` (keep `FONT_ORIGIN` in sync with `app.blade.php`).
    - `connect-src` is `'self'`, the S3 signed-URL origin (client object URL host, or `temporary_url`; derived without network calls), `CSP_CONNECT_SRC` extras, and the Vite dev server (http + ws, also allowed for scripts/styles) only while `public/hot` exists.
    - `default-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'self'`.
    - Residual, accepted: CSP cannot stop malicious code from navigating the page to another site with the key in the URL.
    - Any new third-party resource (script, image host, font, API) needs its origin added here, or it will be blocked. The Pest browser plugin launches Chromium with `bypassCSP: true`, so browser tests never catch CSP violations: check new resources in a real browser (listen for `securitypolicyviolation` events) and keep `SecurityHeadersTest` in sync.
- **Threat model**: `security/threat-model.json` is an OWASP Threat Dragon (v2) model: one STRIDE diagram with trust boundaries (internet, browser, application host, data tier, third parties), every process/store/flow, and threats marked Open/Mitigated with the mitigation. Keep it up to date whenever a change adds an endpoint, data store, external service or trust assumption, or fixes an Open threat (flip it to Mitigated and describe the fix). Open it in Threat Dragon (desktop app or web) to edit; keep the JSON pretty-printed so diffs stay reviewable.

## Upgrading Dependencies

When asked to upgrade dependencies, do not take updates blind. Frontend packages run in the page that holds decryption keys.

1. Update within the cooldown (`sail composer update`, `sail npm update`). Bypass it (`--no-cooldown`) only for a security fix the user approves.
2. Review what changed before keeping it: diff `composer.lock` and `package-lock.json` for newly added packages (including transitive ones), new install/postinstall scripts, changed repository or maintainer, and major version bumps; read the changelog of every major bump and of anything new in the frontend bundle.
3. Run `sail composer audit` and `sail npm audit`; fix or report every finding (accepted advisories are listed in AGENTS.md or the threat model).
4. Run lint, the full test suite including browser tests, and `sail npm run build`. A Playwright bump makes every browser test fail with `PlaywrightOutdatedException` until `sail npx playwright install chromium` fetches the matching browser. Browser tests bypass the CSP, so if an upgrade touches what the page loads, check it in a real browser too.
5. Report to the user which packages changed, anything unusual from step 2, and the audit results.

## Architecture

- **React 19 + Inertia v3 + TypeScript 7**: Frontend uses React components served via Inertia.js. All frontend code lives in `resources/js/`.
- **Current framework baseline**: PHP 8.5.12, Laravel 13, Inertia 3, React 19, TypeScript 7, and Pest 5. Frontend linting uses Oxlint with `oxlint-tsgolint` because `typescript-eslint` does not support TypeScript 7.
- **Hardened serialization**: Cache object unserialization is disabled and sessions use JSON serialization. Deploying the session change invalidates sessions created with PHP serialization.
- **Atomic Design**: Components organized as atoms → molecules → organisms → layouts → pages (`resources/js/components/{atoms,molecules,organisms,layouts}/` and `resources/js/Pages/`).
- **Dedicated logic files**: Business logic separated from React components into services (`resources/js/services/`), hooks (`resources/js/hooks/`), and libraries (`resources/js/lib/`). The crypto module (`lib/crypto.ts`) handles all E2E encryption primitives, and services orchestrate flows (secret sharing, secret viewing, file upload/download, markdown).
- **Controller-based routing**: Standard Laravel controllers and `routes/web.php` — no Folio.
- **Feature flags (independent)**: Two independent Pennant feature flags — `Authentication` (Google SSO, guest links, profile menu) and `FileUploads` (chunked encrypted uploads). Controlled via `FEATURE_AUTH` and `FEATURE_FILE_UPLOADS` env vars. People can fork and toggle them independently. `phpunit.xml` pins both flags to false so tests never depend on the developer's `.env`; tests that need a feature turn it on explicitly (`Feature::purge(...)` + `config([...])`). The flags are enforced server-side, not only in the UI: every Authentication route (login, Google redirect/callback, guest access, guest link creation) and the upload routes are wrapped in Pennant `EnsureFeaturesAreActive`, configured in `AppServiceProvider` to answer 404 when inactive. Uploads need both flags (there are no users without Authentication); file download stays open so already-shared files remain retrievable.
- **Google sign-in allowlist**: `GoogleAccountPolicy` admits a Google account only if its email domain is listed in `AUTH_ALLOWED_DOMAINS` (exact, lowercased), Google marks the email verified, and the `hd` claim equals that domain (Workspace-managed; personal Google accounts using a company address have no `hd`). Every misconfiguration fails closed: empty list, any entry that is not a plain domain, or the old regex `AUTH_ALLOWED_EMAILS` still set. With a single domain the redirect passes `hd` so Google's picker is limited to it. No regex or wildcard support, on purpose.
- **Guest links are single-use**: `GET /guest/{link}` (signed) only renders `GuestAccess`; the "Continue as guest" POST to the same signed URL consumes it via `GuestLink::consume()` (one conditional UPDATE on `used_at`), regenerates the session and starts the guest grant. Consuming on GET would let mail scanners that prefetch links burn them. Reopening the link in the browser that holds the guest session redirects home.
- **Guest access lasts exactly the chosen duration**: the creator picks 1, 7 or 14 days (`GuestLinkDuration` enum, shared to the frontend as `guestLinkDurations`; anything else is a 422). The clock starts at creation, and `expires_at` is both the deadline to accept and the end of access. Accepting sets the encrypted, HttpOnly `guest_access` cookie (`id|token`, expires with the link) alongside the session grant; `guest_links.access_token_hash` stores the token's SHA-256, written by the same UPDATE that consumes the link. The session keeps its global 2-hour idle `SESSION_LIFETIME` on purpose: raising it would weaken signed-in sessions too, so the cookie restores the guest instead.
- **`RestoreGuestAccess` owns the guest grant**: it runs in the web and api groups right after `AddLogContext` (so its own log lines carry `request_id`; `GuestAccess` updates the `guest_link_id` context when it grants or ends access) and before everything else that reads `guest_link_id` from the session: `ClientIdentity`, `Uploader`, shared props, error pages. On every guest request it re-checks the `guest_links` row (ending the grant and clearing the cookie if expired or revoked), and restores a missing grant from the cookie (regenerating the session id). `EnsureAuthenticated` only checks that the grant is present. Links accepted before the cookie existed have no hash and last only as long as their session.
- **Revoking guests**: no UI on purpose. `php artisan guest-links:revoke --user=<creator email or id>` / `--all` (confirms) / `{guest link id}` (rarely known: links have no name, the id is in the URL and in log lines) sets `expires_at = now()`; the equivalent SQL works too. Expire rows rather than deleting them: `pending_uploads` references them and they keep the audit trail. In tests, `Cookie::flushQueuedCookies()` after accepting (see `acceptAndForgetSession` in `tests/Pest.php`): the test app keeps queued cookies across requests, so later responses would re-send the accept cookie.
- **File downloads need a signed URL**: `retrieve()` returns `file_download_url`, a relative temporary signed route (24 h) to `files.download`, which uses `signed:relative` (relative so proxies and scheme changes cannot break the signature). The file id is never returned to recipients. Burning on first download keeps it one-time.
- **Uploads belong to their uploader**: signed-in users and guest sessions can upload (routes use `EnsureAuthenticated`, not `auth:sanctum`); only signed-in users can create guest links, so a guest cannot mint further access. A pending upload stores `user_id` or `guest_link_id`, resolved by `App\Support\Uploader`, and `EnsureUploadOwner` answers 404 on chunk/complete to anyone else (no policy: Laravel policies only see users). Rate limits key guests per guest link (`ClientIdentity`), not per shared IP. Real chunk uploads fail size validation under the Pest browser test server, so browser tests stop at attaching a file; uploads are covered by feature tests.
- **Upload sizes and quota**: `InitiateUploadRequest` caps the declared size at `FILE_MAX_SIZE_GB` and requires `total_chunks == ceil(size / 8 MB)`; every chunk must be at most 8 MB + 16-byte GCM tag and the running total may never exceed the declared size plus tags (`PendingUpload::CHUNK_BYTES` must match `FILE_CHUNK_SIZE` in `crypto.ts`). `UploadQuota` reserves the declared size when an upload starts (abandoned uploads still count) against `FILE_DAILY_QUOTA_GB` (default 100, 0 = off) per `ClientIdentity` over a 24 h window. The quota counts file sizes as users see them, without the ~0.0002% encryption overhead, so 100 GB fits exactly ten 10 GB files.
- **API responses are never cached**: `PreventResponseCaching` in the api group sets `Cache-Control: no-store, private` (Laravel's `cache.headers` skips POST).
- **Log context**: `AddLogContext` (web and api groups, after the session starts) adds `request_id`, `user_id` and `guest_link_id` through Laravel `Context`, so every log line written while serving a request is attributable. Never log file names, secret content, keys or passwords.
- **Expiry at read time**: `Secret::LIFETIME_DAYS` (30) is enforced in `Secret::resolveRouteBindingQuery` and by `secrets:cleanup`; do not hard-code 30 elsewhere.
- **Sessions**: `session.secure` defaults to true unless `APP_ENV=local` (`SESSION_SECURE_COOKIE` still overrides). `session.encrypt` is hard-coded to true (no env switch): payloads must never be readable from the store. Turning it on invalidated sessions created before, which signs everyone out once.
- **Temp file cleanup**: `secrets:cleanup` runs hourly. A pending upload is dead after `PendingUpload::IDLE_MINUTES` (60) without a new chunk, judged by `updated_at` (bumped by every chunk), never by its start, so slow but active uploads survive; uploads cannot be resumed, so idle ones are deleted with their chunk file. The same run sweeps chunk files older than an hour with no upload row and local-download copies (`SharedFile::DOWNLOAD_TEMP_PREFIX` in the system temp dir) older than an hour. The chunk directory is kept `0700` (`PendingUpload::prepareTemporaryDirectory()` also tightens existing ones).
- **Key leaves the URL after viewing**: the viewer drops the `#key` fragment with `history.replaceState` once decryption succeeds (not before, so the retry-with-key flow keeps working).
- **Who can create secrets**: `POST /api/secrets` runs `EnsureAuthenticated`, so with Authentication on only signed-in users and valid guest sessions can create secrets; check/retrieve/download stay public for recipients. API routes only get a session when Sanctum sees a first-party `Referer`/`Origin` (`sanctum.stateful`: the localhost defaults plus `APP_URL`'s host and port), so `APP_URL` must match the public URL or signed-in users and guests get 401 when sharing. `EnsureAuthenticated` checks `hasSession()` first because API calls from other origins carry no session.
- **Chunked file uploads**: Large files are split into 8 MB chunks, each encrypted individually with a derived chunk IV, uploaded via a three-step API (initiate → chunk → complete).
- **Branding**: Colors, logo, and container style are configurable via `config/branding.php` and CSS custom properties (`--brand-primary`, `--brand-secondary`, `--brand-accent`).
- **Shared props via Inertia middleware**: `HandleInertiaRequests` middleware shares `auth`, `branding`, `features`, `appName`, `helpText`, `debug`, and `flash` to all pages.
- **"How it works" modal**: Centralized help lives in `HowItWorksModal`. It is reachable from the profile dropdown when `Authentication` is enabled, otherwise from a standalone info button in the topbar. An optional support line at the bottom of the modal is configurable via `SUPPORT_HELP_TEXT` (read in `config/support.php`, exposed as the `helpText` shared prop); when empty, no help section renders.
- **Error pages**: In production, every error response (any 4xx/5xx) renders the branded `Error` React component via Inertia — nothing falls through to the default framework page. Locally, only predictable user-facing codes (403, 404, 419, 429, 503) are styled so Laravel's debug page stays available for unexpected errors. JSON API requests bypass Inertia and return standard Laravel error responses. Redirects and successful responses are never converted to error pages, and only intentional `abort()` (HttpException) messages are surfaced to the client — raw exception messages are never leaked.
